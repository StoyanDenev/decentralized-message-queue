# v2.25-DSSO-DAPP-SPEC.md — "Sign-In With Determ": the mutual-distrust identity provider (threshold-OPAQUE)

**Status:** AUTHORITATIVE for the DSSO DApp (V1.1-PLAN Bundle A). Single DSSO mechanism doc under the B3 consolidation program. Realizes the design of *Identity provider in an environment of mutual distrust* (academia.edu/80188125) with two owner-chosen improvements — **OPAQUE in place of the paper's SRP**, and a **t-of-n, unordered** threshold in place of the paper's sequential all-node chain. **No FROST, no threshold signature, no block-co-signed assertion** — the paper issues its relying-party token by hash challenge-response over handshake-co-generated keys, so no signature scheme is involved at all.

**Authority:** Stoyan Denev — owner decision: drop FROST, keep the paper's design. This spec supersedes the 2026-07-15 "DLT-B" text, which had re-engineered the assertion into a block-anchored / credential-signature form the paper does not use. Recorded: `DECISION-LOG.md` 2026-07-20.

**Chain surface:** none. DApp-layer protocol over already-shipped primitives; the v1.1 consensus path and the no-migrations lock are untouched.

So `pk_s` reached the client from nowhere trustworthy: an attacker knowing only the victim's **public** `pk_c` picked her own `(sk_s′, esk_s′)`, computed all three client DH values, emitted a valid `server_mac`, and the client accepted — **full IdP impersonation and a shared `sso_key`**, the attacker never recovering `sk_c`. Before fixing it the attack was **re-executed against the shipped `determ_opaque3dh_server`/`_client`** (not merely re-read from the record): the honest client returned `server_mac_ok == 1` and both sides agreed on `session_key`.

   *The correction* is RFC 9807 §4.1.1, which the module had been missing. The AKE transcript now carries `CleartextCredentials{server_public_key, client_public_key, server_identity, client_identity}` under its own `DTM-DSSO-CLEARCRED-v2-` tag; the preamble — hence every MAC and the session key — commits to it; the separate `pk_s`/`pk_c` **arguments are removed**, so a static key can enter a party only through that one MAC-covered transcript field; and **the same bytes are the AAD** under which the §3-step-3 envelope is sealed, so the envelope tag and the transcript MAC commit to one and the same block.

   *What now holds:* the client accepts the server **iff** the peer holds `sk_s` for the `pk_s` the client anchored **and** ran the identical transcript. A party that does not hold `sk_s` is rejected (`server_mac_ok == 0`) and derives no shared key. *What is assumed:* that the client's anchored `pk_s` is authentic — binding is not trust. **Trust boundary, stated plainly.** (i) *At every login after enrolment:* `pk_s` and the identities are the envelope's AAD, so opening the envelope requires the user's password **and** ≥ `t` OPRF responses (the C1/C3 assumption this design already makes); a substituted `pk_s` fails the AEAD tag and the login **aborts before the AKE**, exactly like a wrong password. (ii) *At enrolment:* the authentic `pk_s` must come from the DSSO registration record on chain, resolved through the committee-authenticated light-client chain of custody — genesis pin (`determ::light::anchor_genesis`, `build_genesis_committee`) → per-block K-of-K committee signatures and registry tracking (`determ::light::verify_chain_to_head`) → the committee-**bound** state root (`determ::light::committee_bound_state_root`) → a state proof (`determ::light::read_account_trustless`), with `determ::light::collect_d5_streams` the shipped pattern for reading DAPP_CALL records completely. **Named residual: no DSSO-specific `pk_s` resolver exists in `light/` today** — those functions are the components such a resolver must be built from, not the resolver, so until it ships the enrolment anchor is a requirement on the deployment, not shipped code. An attacker who controlled enrolment owns the account from the start; an attacker who controls only the network can still deny service, observe metadata and guess online (§6), but can no longer be accepted as the IdP. *Rotation:* the DSSO service key is registered to the service domain, not to a committee member, so committee rotation does not rotate `pk_s`; rotating `sk_s` requires re-sealing every user's envelope (the §8 re-deal), and until a user re-seals, a new `pk_s` fails closed at that user's AEAD tag rather than silently taking effect.

   *Permanence.* The domain tags and the encoding are frozen once a deployment exists. **None exists**, so no login transcript had to reproduce and the v1 encoding was **replaced in place** rather than kept beside a v2: a retained v1 would be dead code and a downgrade target — it *is* the impersonable construction. The tags nonetheless moved (`DTM-DSSO-OPAQUEv1-`/`-OPAQUE3DH-v1-` → `…v2-`) so the two encodings can never be confused, the v1 KAT is **retired**, and the v2 bytes are frozen under the same rule. Gated by `determ test-dsso-opaque3dh` (43 assertions, C2-a…C2-g) + `determ test-dsso-login-e2e` (E2E-10), dual-oracle KAT re-derived python-first in `tools/verify_opaque3dh.py`; mutants M1–M6 (drop `pk_s`, drop `pk_c`, drop the identities, bind server-side only, weaken the MAC compare, restore the v1 preamble wholesale) and M7 (re-null the envelope AAD) each RED.

3. **CLOSED (2026-09-17).** Claim C6 was FALSE twice over, and both halves were reproduced before the fix (an isolated harness transcribing the shipped `rp_accept` verbatim; see the DECISION-LOG 2026-09-17 entry). (a) The stateless §5 accept rule verified only that the presenter knew `tenant_key` over an `H1'` of its **own choosing** — `sso_key` never entered verification — so any `tenant_key` holder (which §5 put in *every user's* hands) minted a token for any subject. (b) The freshness legs were evaluated on a **cleartext claim the RP could not authenticate** (it holds no `sso_key`, so it could not recompute `H1'`), so a legitimate user re-presented the same `(H1', H2)` bytes under a substituted claim — different `sub`, fresh nonce, rewritten `iat`/`exp` — and was accepted as another subject. Reproduction also showed the e2e harness's "sounder" reference rule closes (a) but **not** (b), because its accept predicate still reads no field of the claim. **The fix** rewrites §5 below and ships it as a module (`dapps/dsso/assertion.{h,c}`, gate `determ-dsso selftest-assertion`): the claim goes INSIDE the outer MAC, the user presents no tag at all, and the RP accepts only a tag the IdP delivered over the registered channel — so verification depends on the login's `sso_key` and on the IdP's own claim. ## 0. The paper's design, and the two improvements

The paper builds a federated identity provider from **K mutually-distrusting servers**: a user authenticates to the *set*, and no single server (below the trust threshold) learns the user's password or can impersonate the IdP. The paper's concrete construction is (a) an **SRP** augmented-PAKE whose verifier material is split across the servers, (b) evaluated as a **sequential hash chain** (server A -> B -> ... -> G, every server required, in order), (c) issuing the relying-party token by a **dual-hash challenge-response**: the PAKE handshake co-generates a shared key, and the RP accepts iff `H2 == H2'` where `H2 = H(tenant_key, H1')`.

Determ maps the K servers onto its **K-of-K committee** and adopts the paper's framework verbatim except for two owner-chosen improvements:

1. **OPAQUE in place of SRP.** OPAQUE (CFRG, RFC 9807-track) is the modern UC-secure aPAKE: OPRF blinding hides the password from every server, and the envelope adds precomputation-resistance against a stolen verifier — properties SRP lacks. The paper's framework is PAKE-agnostic, so the substitution is drop-in.
2. **t-of-n and unordered in place of the sequential all-node chain.** The paper needs every server, in a fixed order — a latency chain and a single point of failure. Determ thresholdizes the OPRF (Shamir, **t-of-n**): the user blinds the password, **broadcasts** it, collects **any t** blinded evaluations **in any order**, and recombines by Lagrange interpolation. This is exactly the "not all nodes needed, no predefined order" property.

**FROST is not part of this design and never was.** The paper issues its token by hash challenge-response over co-generated keys, not by a server signature — so there is no threshold-signature step to implement, and nothing here composes with FROST.

## 1. Roles

- **Servers O_1..O_n** — the K-of-K committee members act as the IdP servers. (A deployment MAY register an opt-in server set instead; recorded in DAPP_REGISTER.)
- **User U** — holds a password `pw` and an OPAQUE credential.
- **Relying party (RP)** — an off-chain service; registers via v2.18 DAPP_REGISTER, establishing shared `tenant_key` material with the IdP. Challenges/responses and the IdP→RP assertion records ride v2.19 DAPP_CALL.
- **`tenant_key` custody (normative).** `tenant_key` is held by **exactly two principals: the IdP and the one RP that registered it**. It never reaches a user, a wallet, the chain or any third party. It is a symmetric MAC key, so a holder can compute every value an RP-local rule accepts; it is also the RP's identity on the registration channel. Registration establishes it as `tenant_key = HKDF-SHA-256(registration secret, info = "determ-dsso/tenant-key/v1" ‖ rp_id ‖ u64(key_epoch))`. Two epochs govern its life: `key_epoch` is bumped on every key rotation (an assertion naming any other `key_epoch` is rejected `DSSO_E_TRUST`), and `reg_epoch` is bumped only when the relationship is re-established, which also rotates the pairwise subjects of §5. An earlier draft of §5 had `U` compute `H2 = H(tenant_key, H1')`, which contradicted this line and was the direct cause of defect C6(a) — §0.0(3); that sentence is gone.
- **Threshold t** — how many servers must respond. Default **t = n-1** (tolerates one down/dishonest server; below-t collusion cannot recover the password). Per-deployment; recorded at registration.

## 2. Primitives — all already shipped

| Primitive | Role | Ref |
|---|---|---|
| P-256 RFC 9497 OPRF/VOPRF | the threshold OPRF substrate (prime-order group + hash-to-curve + DLEQ) | CRYPTO-C99 §3.9b |
| Shamir over the P-256 scalar field | user-dealt t-of-n shares of the OPRF key | shipped (`test_wallet_shamir*`) |
| OPAQUE envelope (AEAD + HKDF) | seals the user credential; unsealed by the OPRF output | ChaCha20-Poly1305 / AES-GCM + HKDF (§3.1/§3.4/§3.5) |
| SHA-256 / HMAC / HKDF | the dual keyed-hash challenge-response (`binder`/`tag`), the pairwise-subject derivation, and key derivation | §3.1 |
| Ed25519 | user credential key; committee identity keys | §3.2 |
| v2.18 DAPP_REGISTER / v2.19 DAPP_CALL | RP registration; challenge/response transport | shipped |
| Light-client committee resolution | RP resolves the on-chain committee (IdP server) set | shipped |

Zero new primitives, zero new hardness assumptions. The threshold OPRF runs on the shipped P-256 RFC 9497 stack because that is the shipped stack with the required group operations (point add, scalar inverse, hash-to-curve); X25519 lacks them. This is an implementation substrate, not a change to the paper's design.

## 3. Registration

1. U picks `pw` and generates an OPAQUE credential (a fresh **P-256** keypair `cred = (sk_c, pk_c)` — the DSSO identity is separate from the on-chain Ed25519 identity; single-curve P-256 is what the OPAQUE-3DH AKE requires; owner decision 2026-07-21, DECISION-LOG, supersedes the earlier "Ed25519 keypair" text that predated the RFC-9807 AKE choice).
2. U computes the OPRF key `k` and **deals it as t-of-n Shamir shares** `k_i` to the servers (user-as-dealer — no DKG, no server-side ceremony; an inconsistent dealing can only self-DoS U's own account). Each server stores its `k_i`; the share commitments `PK_i = k_i·G` are published so responses can be checked (§4).
3. `y = OPRF_k(pw)` computed locally; `envelope = AEAD_{HKDF(y)}(cred_sk ; AAD = CleartextCredentials)` where `CleartextCredentials = {server_public_key, client_public_key, server_identity, client_identity}` (RFC 9807 §4.1.1) — the byte-identical block the §4-step-5 AKE transcript binds. The envelope is stored (client-side and/or on-chain). The AAD is what makes the `pk_s` the client later anchors AUTHENTIC: opening the envelope needs `pw` and >= t OPRF responses, so a substituted `pk_s` fails the AEAD tag and the login aborts before the AKE (§0.0(2)).
4. RP registration (once per RP): v2.18 DAPP_REGISTER establishes the RP's identity and shared `tenant_key` material with the IdP.

## 4. Login (t-of-n threshold OPRF — unordered)

1. U blinds: `r` random, `B = r·H2C(pw)`.
2. U **broadcasts** `B` to the servers — no ordering, no server-to-server communication, no per-server state beyond the stored share.
3. Each responding server returns `Z_i = k_i·B` with a DLEQ proof `pi_i` (shipped P-256 VOPRF) that `Z_i` is consistent with its published `PK_i`.
4. On **any t** valid responses, in **any order**: U discards any response whose `pi_i` fails, Lagrange-combines `Z = sum(lambda_i·Z_i) = k·B`, unblinds `N = r^{-1}·Z = k·H2C(pw)`, finalizes `y`.
5. `y` unseals the envelope -> `cred`. The OPAQUE handshake **co-generates a shared session key** between U and the IdP (the paper's "co-generation of a common key"). No server saw `pw`; below-t servers cannot combine.

## 5. Assertion to the RP (the paper's dual keyed hash — no signature)

**This section was rewritten on 2026-09-17 to close defect C6 (§0.0(3)); it is implemented, not merely specified, by
`dapps/dsso/assertion.{h,c}` and gated by `determ-dsso selftest-assertion`.** The construction is still the paper's:
an inner keyed hash under the login's co-generated key, an outer keyed hash under the RP's registration key. No
signature, no FROST, no block co-sign, no new primitive — HMAC-SHA-256 throughout.

### 5.1 The claim, and its canonical encoding

The IdP asserts a SIWE-class claim
`(iss, sub, aud, sid, nonce, iat, exp, reg_epoch, key_epoch)`, where `sub` is the **pairwise** subject of §5.4,
`aud` the intended audience, `sid` the request/session id the RP opened for this login, and `nonce` a 32-byte
single-use value. Its canonical encoding is unambiguous — fixed field order, every variable-length field prefixed
by a big-endian u64 length, the whole prefixed by a domain tag:

```
canon(claim) = LP("determ-dsso/assert/claim/v1")
             ‖ LP(iss) ‖ LP(sub) ‖ LP(aud) ‖ LP(sid)
             ‖ nonce(32) ‖ u64(iat) ‖ u64(exp) ‖ u64(reg_epoch) ‖ u64(key_epoch)
where LP(x) = u64be(len x) ‖ x
```

### 5.2 The two legs

```
binder = HMAC-SHA256( sso_key,    LP("determ-dsso/assert/binder/v1") ‖ canon(claim) )
tag    = HMAC-SHA256( tenant_key, LP("determ-dsso/assert/tag/v1")    ‖ canon(claim) ‖ binder )
```

This is the paper's `H2 = H(tenant_key, H1')` with `H1' = H(sso_key, challenge)`, with the two corrections C6 forced:
the "challenge" **is** the canonical claim, so the inner leg commits to every field the RP will act on; and the outer
leg's message is `canon(claim) ‖ binder`, **not `binder` alone**, so the value the RP checks commits to the claim as
well as to the login.

### 5.3 Who computes what, and the accept rule

- The **IdP** holds `sso_key` (from the §4-step-5 handshake), `tenant_key` (§1) and the per-user `user_root` (§5.4);
  it computes `sub`, `binder` and `tag`. **`U` computes no outer leg and never holds `tenant_key`.**
- **IdP → RP**, over the registered v2.19 DAPP_CALL channel: the **reference `tag`**. The RP retains it in a bounded
  table for `T_max + skew` from the claim's `iat`.
- **IdP → U → RP**, front channel: the user is given, and presents, `(claim, binder)`. **The user is given no `tag`
  and presents none.**

> **Accept rule.** The RP accepts iff (i) the claim's `key_epoch` and `reg_epoch` are its current ones; (ii)
> `HMAC(tenant_key, LP(DS_TAG) ‖ canon(claim) ‖ binder)` recomputed over the PRESENTED claim and binder equals, in
> constant time and over the full 32 bytes, one of the reference tags the IdP delivered to this RP and has not yet
> expired; (iii) the authenticated `sid` is the session THIS verifier is completing; (iv) `iat ≤ now + skew`,
> `exp > now` and `exp − iat ≤ T_max`; and (v) the claim's `nonce` has not been accepted before within its retention
> window.
>
> Leg (iii) is not redundant with the `sid` inside the MAC. The MAC keeps the IdP's statement about `sid` honest; the
> comparison is what stops a party who influenced WHICH `sid` was asserted from fixating someone else's session with a
> token perfectly valid for its own — login-CSRF. The session id the verifier compares against is the one the RP itself
> opened, never a value read from the presentation. Correspondingly the IdP MUST take `aud` and `sid` from its own
> state and never from an untrusted party: the module authenticates whatever it is asked to assert.

Why it must be this and not something simpler: an accept rule that is a pure function of `tenant_key` and
presenter-supplied bytes can always be satisfied by a `tenant_key` holder — it need only run the honest minting
algorithm with an `sso_key` of its own. That was the old rule, and it is exactly defect C6(a). The only escapes are an
asymmetric signature (forbidden by §7) or an accept rule that consults per-login state the IdP delivered. §5 takes the
second, which is what "the RP computes `H2'` **from the same material**" always had to mean.

**No cleartext field of an unauthenticated claim is compared against anything.** The verifier authenticates first and
reads the claim afterwards; that is why the MAC covers `aud`, `sid`, `sub`, `iss` and both epochs. The epoch check is
the one unavoidable exception, because it selects *which key* the verifier is entitled to verify under.

**Fail-closed, with a named `dsso_status` for every rejection:** a missing or over-long input is `DSSO_E_ARG`; an
unreadable clock (`now == 0`) is `DSSO_E_UNAVAILABLE`; an unknown relying party, a rotated-out `key_epoch` or a previous
`reg_epoch` is `DSSO_E_TRUST`; a tag matching no live reference is `DSSO_E_CRYPTO`; a clock-leg failure is
`DSSO_E_EXPIRED`; a seen nonce is `DSSO_E_REPLAY`; a nonce cache with no free or expired slot is `DSSO_E_UNAVAILABLE`
— the verification is REJECTED rather than accepted without memory, because accepting while unable to remember is
accepting a replay. Nothing is written and no table mutated on any rejected path.

### 5.4 Pairwise subject identifiers

```
sub = HMAC-SHA256( user_root, LP("determ-dsso/assert/pairwise-sub/v1") ‖ LP(rp_id) ‖ u64(reg_epoch) )
```

`user_root` is a 32-byte per-user secret the **IdP alone** holds, fixed at enrolment, never on the chain and not derived
from `sso_key` (which is per-login and would make the subject unstable). The result is DIFFERENT for each relying party
— two RPs comparing subjects learn nothing, since the key is one neither holds — and the SAME for one relying party
across every login. The IdP derives it; it is never an input a caller supplies.

**On re-registration** (`reg_epoch` bumped) the subject **changes** and the RP must re-link its accounts. That is the
fail-safe default: a re-registration means the relationship was re-established — a new operator, a post-compromise
re-enrolment — and carrying the identifier across would hand the new holder the previous holder's linkage to every
user. An operator wanting account continuity rotates `key_epoch` and keeps `reg_epoch`.

### 5.5 Bounded state at the RP

Both RP tables are fixed-size arrays, never heap-grown and never proportional to attacker input: a nonce cache and a
reference table. An entry is retained until `iat + T_max + skew`, which is at least `exp + skew` for every claim that
passed the clock legs — so an entry is forgotten only once the clock alone already rejects any token carrying it. On
insert the module takes an empty slot, else a slot whose retention has elapsed; **it never evicts a live entry**, and a
table with no free or expired slot is a rejection. Sizing is a deployment parameter: the nonce cache must exceed peak
ACCEPTED logins per retention window, and only assertions the IdP actually issued can consume a slot.

An AUTHENTICATED party can wedge a verifier by completing enough real logins to fill the nonce cache inside one
retention window, after which honest logins fail closed until entries expire. That is the price of never forgetting a
live nonce, and it is the right side of the trade — the alternative accepts replays. The levers are deployment ones:
size the table above peak, and apply the per-account login rate limit §6 already requires. A per-subject slot quota
would bound it further and is not implemented.

**Residuals, recorded rather than papered over.** The `binder` is a bearer secret in transit — front-channel
confidentiality is the deployment's (TLS or the AKE-derived channel), and the single-use nonce, `T_max` and the `sid`
binding bound what a stolen one is worth. The IdP→RP reference channel is authenticated by the registration, not by
this module; an adversary who can write to it *is* the IdP for that RP, which no symmetric construction can improve on.
A compromised IdP can assert anything — the mutual-distrust property is a property of the *login* (C1/C3/C4), not of
the assertion.

*Optional, off by default:* a deployment wanting a public login audit trail MAY additionally emit a DAPP_CALL record of
`(sub, aud, iat)` — an audit anchor only, not part of the authentication, and not the assertion mechanism.

## 7. Explicit non-goals

- **No FROST / threshold signature / DKG** — the paper co-signs nothing; the OPRF key is user-dealt.
- **No block-anchored assertion** — the token is the paper's hash challenge-response (an earlier draft's block-anchoring is dropped).
- **No post-quantum claim; no assertion-traffic anonymity; no phishing defense** — out of scope.

## 8. Recovery / rotation

- Password change / share refresh / server churn: U re-deals fresh shares + envelope (user-as-dealer; no DKG), authorized under U's chain identity key.
- Chain-identity key loss/compromise: v2.26 ROTATE_KEY (unchanged precondition for production).

## 9. Green gates before Bundle A merge

- **G1** t-of-n identity: Lagrange over every t-subset == direct OPRF evaluation.
- **G2** per-response DLEQ reject paths (tampered response rejected).
- **G3** envelope AEAD/HKDF KATs.
- **G4** end-to-end: register -> login (t-of-n; one server down; one byzantine) -> dual-hash assertion -> RP accepts.

## 10. Relation to earlier drafts

The 2026-06-07 "DLT-A" and 2026-07-15 "DLT-B" drafts re-engineered the assertion (block-anchored DAPP_CALL + committee/user signatures) — a Determ-specific mechanism the paper does not use. This spec drops that: the assertion is the paper's dual-hash challenge-response, and the "DLT-A/-B" labels are retired. What carries over from those drafts (and is correct) is the t-of-n OPRF on the shipped P-256 stack. FROST removal is unchanged (`FROST_DEVIATION_NOTICE.md`) — this design needs no threshold signature.

## 11. The OTHER role: DSSO as a WALLET-RELYING PARTY (Reg. (EU) 2024/1183 Art. 5b)

Everything in §§0-10 is DSSO's role as a **private, non-notified identity provider** for its own relying parties: it authenticates a RETURNING user (threshold-OPRF + OPAQUE-3DH) and asserts to an RP (the §5 dual-hash token). DSSO is being built toward a **second** role, and only these two.

**The second role is wallet-relying party.** At **ENROLMENT**, an EUDI Wallet Unit presents **Person Identification Data** to DSSO; DSSO verifies that presentation and binds the subject to a DSSO account. This is a different party, a different protocol and a different trust source from §§0-10, and the two must not be conflated: in §§0-10 DSSO is the thing being trusted, and here DSSO is the thing doing the trusting.

**Where it sits relative to the login.** The PID flow happens **once**, before the §3 registration has anything to be registered against; the §4 login happens every time afterwards. They meet at exactly one place — the ACCOUNT — and nowhere else. No PID attribute, no raw identifier and no presentation byte enters the §4 login path, the §5 assertion path, or the chain. What the login path can learn about an enrolment is that an account carries a binding, and at what assurance level.

**DSSO never claims the wallet's level for its own later logins.** Identity proofing at enrolment is INHERITED from the PID (CIR (EU) 2015/1502 Annex §2.1.2), which the wallet issues under a notified scheme; DSSO records what it verified. DSSO's own authentication is the separate question §§0-10 answer, targeted at EQUIVALENCE TO level substantial via Annex §2.2.1 (two factors from different categories) and §2.3.1 (dynamic authentication). "Equivalent to" is the only phrasing this repository uses; never "certified", "notified" or "compliant".

**What is implemented, and what is not.** The verification and account-binding half is SHIPPED and gated — [`DssoPidVerification.md`](DssoPidVerification.md), gate `determ-dsso selftest-pid` (`tools/test_dsso_pid.sh`, FAST). The format is **SD-JWT VC** with a Key Binding JWT; **ISO/IEC 18013-5 mdoc is NOT implemented**, so an mdoc-only wallet is out of scope until a second increment. Nine separately-testable rules: bounded structure, issuer trust from a configured PID Provider trust anchor list (**ARF OIA_12**), ES256, selective disclosure, holder binding (**ARF OIA_02**), audience, the DSSO-issued nonce, freshness, IETF Token Status List (**fail-closed**), and assurance. Account binding requires the holder's own fresh re-authentication plus a single-use challenge, allows no silent double-binding or re-binding, and stores only a keyed pseudonym — never a raw national identifier or document number.

**NOT implemented, and external.** **OpenID4VP** (OIA_03/OIA_03b/OIA_04) — this module verifies a presentation some transport already delivered. The **wallet-relying-party ACCESS CERTIFICATE** (**RPA_01..RPA_06**) — obtaining it requires registration with a **Member State registrar**, which cannot happen in a repository; nothing in DSSO authenticates DSSO *to* a wallet, and a real deployment needs that certificate before a wallet would answer a request at all. No eIDAS Trusted List (ETSI TS 119 612) is fetched or parsed. Passing the gate is not a compliance claim.
